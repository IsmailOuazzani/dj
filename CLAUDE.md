# DJ Controller

A from-scratch personal build of a DJ controller. Scope (hardware vs. software split, language, frameworks) is not yet decided — ask before adding tooling or dependencies.

## Working rules

- **Never `git commit` without being asked.** Make file edits freely, but leave them uncommitted. Wait for an explicit "commit" before staging.
- **After editing `mixxx/ISMA-3000.midi.xml`, always run `cd firmware && task mixxx:sync`.** Editing the in-repo file changes nothing that Mixxx can see — Mixxx loads its own copy from `~/.mixxx/controllers/` (Linux) or the sandboxed container path (macOS), and `task mixxx:sync` copies it across. It's idempotent, so run it every time rather than deciding whether it's needed. Skipping it means the user tests a stale mapping and the resulting bug hunt lands on the firmware instead of the config. Report that you synced.
- **Always include a plain-text URL when mentioning a specific part.** Any time you name a specific part number, SKU, module, IC, breakout, cable, cap, etc. — in chat replies, prose, tables, notes, or file edits — paste its full digikey.ca (or vendor) product URL alongside it as **bare text**, NOT a markdown `[text](url)` hyperlink. The user should be able to triple-click and copy the URL out. This applies universally: a one-line mention in a chat reply gets a URL just like a BOM row does. If you don't have a verified URL, use the deterministic keyword-search fallback (`https://www.digikey.ca/en/products/result?keywords=<PN>`) per the URL-invention rule below — never omit the link.
- **Always include full pasteable URLs in hardware comparison tables.** Whenever a table compares hardware options (parts, modules, ICs, etc.), every row that names a specific part must include the **full URL** to its digikey.ca product page (or vendor product page if not on Digikey) — as **bare text**, NOT a markdown `[text](url)` hyperlink. A dedicated "Link" column is the clearest layout. The user should be able to triple-click the cell and copy the URL out.
- **NEVER invent or guess a URL.** Product-detail URLs (e.g. `digikey.ca/en/products/detail/<mfr>/<pn>/<numeric-id>`) contain an internal numeric ID that cannot be derived from the part number — guessing it will resolve to a **completely different product** and mislead the user into buying the wrong part. If a URL isn't already in the BOM / conversation / a tool result you can cite, you have three options and only three: (a) fetch it with WebFetch / WebSearch and paste the resolved URL, (b) fall back to a keyword-search URL like `https://www.digikey.ca/en/products/result?keywords=<part-number>` which is deterministic and safe, or (c) explicitly flag the URL as missing and ask. Never fabricate a `/detail/` URL to fill a "Link" column.
- **BOM part tables MUST have a dedicated `Link` column — no URL-in-Notes.** Every table in BOM.md that lists specific purchasable components must have a `Link` column, and URLs go there. Do NOT stuff URLs at the end of a Rationale/Notes cell — that hides them from mechanical audit (`grep`, awk, spreadsheet import) and makes the "does every row have a URL?" check impossible to run cleanly. When adding a new table, include the Link column from the start; when editing an existing table that lacks one, add it before appending any new rows. Subtotal/summary rows leave Link empty.
- **When a tool/library/toolchain behaves unexpectedly, read the docs before guessing.** If a build flag, config option, or API doesn't work the way you assumed, stop iterating — fetch the official docs, search for the specific issue (GitHub issues, community forums), and only then change the approach. Don't burn cycles trial-and-erroring quoting, ordering, or flag combinations when the answer is one WebFetch / WebSearch away.
- **Wiring instructions MUST cite the exact silkscreen label on the specific breakout, not the chip's native pin name.** Chip datasheets and breakout PCBs routinely disagree — MCP23017 die pin `GPA0` is silkscreened `A0` on the Adafruit 5346; ATmega32U4 `PB4` is silkscreened `D8` on many Arduinos; a CD4067 `SIG` may be labeled `Z` on the breakout. If you tell the user "wire to GPA0" they will hunt for a pad that isn't there and come back with "is that A0, D0, or B0?" — a dead-loss round-trip. **Rule:** every wiring instruction (chat replies, comments, `hardware-docs/`, firmware pin defs) MUST name the pad/pin exactly as it is printed on the specific PCB in hand, verified against that board's pinout page/datasheet OR an existing `hardware-docs/<board>.md` note. If the mapping is non-obvious and no per-board note exists yet, resolve it once via WebFetch, then either extend an existing hardware-docs file or create a short new one so the next agent skips the lookup. When both the chip pin and the breakout label matter for context (e.g. reading firmware that uses `mcp.pinMode(0, ...)`), cite both — "MCP `GPA0` = pad labeled `A0` on the Adafruit 5346" — never just the chip name in isolation.
- **Red-flag any cannot-buy-today part as a blocker.** The SPEC's in-stock-now rule disqualifies parts you cannot put in a cart today: 0 stock at Digikey Canada, backorder, NRND, Last Time Buy, Obsolete, Discontinued, or "ships in N weeks" (non-stock with mfr lead). Any of those → 🛑 blocker at the top of the report, not a passing footnote. **However**, a non-zero manufacturer *restock* lead time on a part that still has >0 Digikey CA on-shelf stock is NOT a blocker — the rule is "can I buy one right now," not "how long until Digikey re-stocks." Note the restock clock in the row's rationale if it's long enough to matter for a v2 reorder, but do not escalate to 🛑.
- **Subagent prompts MUST cite SPEC.md and CLAUDE.md and require they're read first.** When spinning up a subagent for any task touching this project, the spawning prompt MUST include the absolute paths `/Users/ismail.ouazzani/code/dj/SPEC.md` and `/Users/ismail.ouazzani/code/dj/CLAUDE.md` and explicitly instruct the subagent to read both files in full before doing anything else. Don't assume the subagent will discover the project rules on its own — non-negotiable, every time.

## Parts research rules (Digikey)

**Sourcing constraint: Digikey Canada (digikey.ca) only, prices in CAD.** All v1 parts must be orderable through digikey.ca. The user is in Canada — quote CAD, link to digikey.ca product pages, and don't recommend off-platform alternatives (AliExpress, eBay, Adafruit-direct, etc.) even when cheaper or better-feeling. Many Adafruit/SparkFun breakouts *are* carried by Digikey under their own P/Ns; check before declaring something off-platform.

When pricing components for this project, agents should:

1. **Filter by "In Stock" before browsing.** Many DJ-grade audio pots/faders (ALPS RSA0N, RK09K) show up but are NRND/obsolete with 20+ week lead times. Filter early to avoid dead ends.
2. **Check whether Adafruit/SparkFun breakouts are on Digikey before treating them as off-platform.** Many are (e.g. SparkFun BOB-09056 CD4067 breakout is Digikey `1568-09056-ND`). Search by SparkFun BOB/COM/PRT or Adafruit PID numbers.
3. **For pot features (detent, taper), search by manufacturer-series suffix, not part number.** E.g. TT P160KN**PD** = center-detent; Same Sky PT01-D**xxx**-B**xxx** = linear B-taper. Confirm from the datasheet, not the Digikey filter.
